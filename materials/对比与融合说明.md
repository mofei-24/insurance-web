# 两份JSON的对比与融合说明

新文件：`借款人意外伤害保险_融合语义树.json`。

融合对象为建模方法。业务依据仍是《中国人民财产保险股份有限公司借款人意外伤害保险（2022版）条款》，不是将人保意外险和同方寿险的保险责任拼成一份合同。原两份JSON均未修改，输入摘要记录在新文件的`provenance`中。

## 1. 对比结论

| 方面 | 同方.json的做法 | 原人保1.1.1版的做法 | 融合版选择 |
|---|---|---|---|
| 事实与规则分离 | `facts`独立声明18项事实，提供类型、提问、输入来源 | 事实说明集中在`required_case_object`，节点常用整段自然语言 | 建立独立`facts`，包含类型、审核状态要求、缺失策略、比例边界与原文引用 |
| 条件表达 | `condition`使用`fact`和`all/any/not/gte`表达逻辑 | 多数`condition`是自然语言，金额已有部分表达式 | 将决策条件转成结构化表达式；共享逻辑存入`rules`，不重复展开免责 |
| 流程分支 | `routes`集中记录true/false/unknown，节点类型统一 | 多种`on_true/on_false/on_clear`等字段并存 | 统一`nodes.kind`与`routes`；另外保留review用于冲突、无效输入和口径争议 |
| 不完整信息 | `NEEDS_INPUT`与`NEEDS_REVIEW`分开 | 已规定未知不等于否，但许多缺失处理是文字 | 未知、争议和给付条件待履行分别输出，不用缺失值代替零或否 |
| 法律效果 | `effects`同时表达保险金、合同终止、现金价值、受益权等 | 终端多为一个`outcome`描述 | 使用累积`effects`，已成立责任、已算金额、受益人状态、返还义务分别保留 |
| 原文追溯 | `sources`存原文、文件、章节路径和行号 | 新增依赖部分有`source_evidence`，其他节点多为章节号 | 全部核心事实、规则、节点关联统一`sources`，附人保原文摘录与定位 |
| 责任间依赖 | 本文件主要建模单一身故责任，未见跨责任`depends_on` | 有身故对伤残已付记录的扣减及共享限额关系 | 保留`responsibilities`、`responsibility_relations`及12条详细`depends_on` |
| 金额及历史记录 | 基本保额和现金价值作为输入，声明不输出净赔款 | 区分保额时点、已付快照、同一合同/被保险人及重复扣减 | 保留历史记录作用域、时点和完整性；将更多公式转成运算树 |
| 未展开条款 | `scope`和`unresolved`明确局部结论限制 | `known_limits`列出待完善问题 | `unresolved`记录问题、受影响节点、处理方式和原文引用；关键问题进入审核门槛 |

同方文件的最大优势是“事实—条件—分支—效果—原文”分层清楚。人保依赖版的优势是能够表达“另一责任的历史给付如何改变当前金额”，并处理共同限额。这两种结构可以同时使用：流程边决定走哪里，依赖边决定计算前需要什么。

未通过文件结构推断任何一方真实核赔准确率更高；节点数、字段数和格式完整性都不能替代案例评估与业务审核。

## 2. 哪些做法没有直接照搬

- 同方寿险的“两年内自杀”不是本意外险规则；本保险的自杀免责没有写该两年限制，不能移入。
- 同方文件中的60日宽限期、现金价值退还、保单借款抵扣均属于其自身条款。人保文件使用自身第3.1条交费规定，并独立核查剩余全年保费先行补交要求。
- 同方把多项关联条款汇总为一个`related_terms_resolved`事实，适合局部核对，但不能当成完整状态机。本版将保障期间/资格/缴费、合同告知审核、受领人、补交保费分别处理，仍明确需要外部专业认定的部分。
- 同方两条路径重复展开“其他免责”表达式，后续更新容易不一致。本版将16项免责存入共享`rules`，由X01引用。
- 同方外部标准缺失信息只描述其自身资料范围。本版的`sources`均为当前人保Markdown，不使用同方摘录作为人保规则依据。

## 3. 新文件的结构

```text
provenance / scope          输入来源、产品范围与局部结论限制
facts                       70个类型化事实定义，缺失/冲突不默认为否
rules                       19个共享逻辑规则，含16项免责
nodes                       53个入口、决策、分流、计算和结果节点
responsibilities            身故、伤残两项责任
responsibility_relations    2类跨责任关系：已付扣减、共享限额
depends_on                  12条详细依赖，分布在计算节点和共享限额规则
shared_rules / amount_rules 共同限额及相关日期保额接口
sources                     51个原文定位单元
unresolved                  尚需专业确认或外部系统处理的事项
migration                   与旧节点ID的对应及主要调整
```

`source_refs`指向原文证据，`depends_on`指向责任或规则输出，`routes`指向下一流程节点，三者各司其职。

## 4. 融合过程中修正的旧路径问题

1. **宣告死亡独立分流。** D01根据`death_mode`选择普通身故D02或宣告死亡D03。宣告死亡不再先要求普通身故日期或180日结果。
2. **伤残评定共同检查。** 无论按治疗已结束路径还是按第180日身体情况评定，都经过A05和多处伤残适用检查，避免绕过合并评定。
3. **既有残疾与比例缺失分开。** A06只判断事故前是否已有残疾；有既有残疾时缺少原有比例，A07进入金额待核定，不转成“无既有残疾”。
4. **例外有明确括号。** EX03为`故意自伤 OR（自杀 AND NOT 自杀时无民事行为能力）`。自杀例外不会扩大到故意自伤，也不直接表示保险责任成立。
5. **定义冲突先核实。** 对非本意定义与自杀例外、感染定义与免责措辞等交叉解释，设置`DEFINITION_REVIEW`审核门槛；本版不擅自解决法律解释争议。
6. **保留已得出的效果。** 责任局部通过后，即使缺金额、受领人或补交保费资料，仍保留责任结果。受益人失权不直接改写成保险责任消失。
7. **补交保费单独出口。** `PREMIUM_SETTLEMENT`未通过时输出`SETTLEMENT_PENDING`，不直接拒赔或声称已经付款。
8. **金额依赖完整保留。** D04/D07读取已付伤残金，D04/D07/A09读取LIMIT01；确认空账本与缺失账本分开，同笔金额不重复扣减。
9. **返还金额区分原付款与已履行返还。** 生还后的返还核查读取原宣告死亡付款及已返还金额，部分返还、冲销口径未核实时进入复核。
10. **数值有合法性检查。** 比例限制在0至1；合并后比例小于原有比例、累计已付超核定上限等情况转复核，不用截零掩盖矛盾。

## 5. 两种关系如何同时工作

身故局部责任成立后，执行D04：

```text
D04 流程计算节点
  depends_on → RESP_DISABILITY：身故前实际已付的伤残金
  depends_on → AMOUNT01：实际身故日的本项保额
  depends_on → LIMIT01：同合同同一被保险人的剩余共享限额
  formula    → min(max(0, 保额－已付伤残金), 剩余限额)
  next       → 受领人与给付条件核对
```

若固定保额为100万元、已付伤残20万元，无其他给付且各项口径均确认，则身故金额为80万元；不会对已减过的剩余限额再扣20万元。

没有伤残给付不是“身故责任缺少前置责任”。只有核实了完整账本并确认无给付，扣减才为0；记录未知时金额为null，保留已经通过的局部责任。

## 6. 结果代码与效果分开

| code | 表示什么 |
|---|---|
| LOCAL_PASS | 当前模型范围内核对通过，未执行真实给付 |
| LOCAL_FAIL | 所选责任路径的必要条件明确不成立，或确认适用免责 |
| NEEDS_INPUT | 当前实际访问路径缺少必要事实、鉴定、记录或金额 |
| NEEDS_REVIEW | 资料冲突、数值非法、受益人争议或适用口径未决 |
| SETTLEMENT_PENDING | 局部责任和金额已核对，但给付条件待满足/核实 |

`effects`另外记录责任局部通过、核算金额、受益人失权、对被保险人保险责任终止、返还义务等。结果代码不是一项“全部推翻”的开关。

## 7. 检查与使用边界

运行`validate_fusion.py`可检查所有引用、表达式、原文定位、节点可达和求值循环，并验证合成案例。输出为`validation_report.json`；`example_traces.json`给出4类示例路径及依赖解析记录。

该脚本是可重复的局部规则验证器：它使用已经确认的合成事实、历史给付记录与保额适配结果。没有实现PDF/OCR、医学鉴定、真实保险业务接口、完整合同状态机或支付服务。日期边界、标准版本、递减保额限额时点及并发占额等事项仍需相应外部审核/系统支持。

旧图与旧JSON仍保留，融合版使用新的文件名与目录；旧ID的含义调整可在`migration`中查看。
