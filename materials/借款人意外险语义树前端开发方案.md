# 借款人意外险语义树前端开发方案

## 一、目标与交付范围

首版面向两类使用者。项目演示者可以从一个案例出发，讲清楚“依据哪条原文、经过哪些判断、为什么得到这个结果”。条款审核者可以从一句原文反查规则，并通过只改变一项事实的对照案例，找出提取错误、计算错误或尚待确认的业务口径。

建议交付一个可本地启动、可静态部署的中文网页，包含条款浏览、语义图、案例验证三个联动视图。首版使用固定版本的人保 2022 版条款和合成案例，桌面电脑优先。展示结果统一使用“局部责任通过”“金额待核定”等模型用语。账户、在线编辑规则、真实理赔接口与多险种管理放到后续需求评审。

## 三、开源方案与技术选择

| 方案 | 可直接借鉴的能力 | 在本项目中的取舍 |
|---|---|---|
| React Flow + elkjs | React 节点卡片、左右布局、多个分支出口；ELK 可根据指定端口安排节点和连线 | 首选。四种判断结果可以有独立端口，便于在中文节点旁标出实际选中的分支。[官方多端口示例](https://reactflow.dev/examples/layout/elkjs-multiple-handles) · [elkjs 项目](https://github.com/kieler/elkjs) |
| AntV G6 | 图数据、布局和多种渲染方式，适合浏览复杂关系 | 若后续重点转向跨险种关系探索，可选作关系图组件。首版采用一套渲染器，以便图、卡片和步骤列表使用同一选中状态。[G6 项目](https://github.com/antvis/g6) |

技术组合建议为 React、TypeScript、Vite、React Flow 和 elkjs。折叠通过业务分组与可见节点集合自行实现；React Flow 示例目录里的 Expand and Collapse 标有 Pro，首版仅参考其交互思路。图布局只在展开分组、切换责任或尺寸变化时计算，案例逐步播放仅更新节点状态。[React Flow 示例目录](https://reactflow.dev/examples)

## 四、复杂语义树的展示结构

### 4.1 首屏用责任总览，点击后进入局部流程

融合图含 22 个判断节点、2 个分流节点、7 个计算节点、3 个入口或阶段通过节点、19 个结果节点。按出口逐条统计，仅“需人工复核”同一终点就有 36 个出口指向它，“需补充事实”有 19 个。若将每条连线都拉到画布最右侧，最抢眼的将是两束异常连线，普通身故与宣告死亡的区别反而很难看清。

建议保留三个阅读层级，每层回答一个具体问题。

| 层级 | 主画布的形式 | 进入与返回 |
|---|---|---|
| 责任总览：这份保险保什么？ | 左侧是共同前提，中间上下两行分别为身故、伤残责任，右侧是共用的受领与给付条件。身故行内另设“宣告死亡后生还 → 返还核查”出口 | 默认进入；选择阶段或责任后下钻，顶部保留当前位置 |
| 局部流程：这项责任怎样判断？ | 一次铺开一段有向流程，按执行顺序从左到右排；分支上下排列，合流处保留同一节点。左右两端标出来自哪一阶段、继续到哪里 | 点击跨阶段出口平移到相邻阶段；返回时恢复原选中节点与视口 |
| 节点详情：这一步凭什么成立？ | 右侧抽屉按类型显示事实清单、逻辑分组或计算明细，原文与节点并列可读。节点 ID 收在标题副行 | 点节点打开；选原文时只更新证据区域，保留当前流程位置 |

下面是总览的连接关系。方括号是可展开的阶段，箭头表示存在对应流程；只有实际运行后才标记某例走过的箭头。

```text
[身份、保障、意外及免责核查] → [选择责任]
                               ├─ 身故 ┬─ 普通身故 → 身故金额核算 ──────┐
                               │       └─ 宣告死亡 ┬─ 未生还 → 宣告死亡金额 ┤
                               │                  └─ 已生还 → 返还核查   │
                               └─ 伤残 → 评定与比例 → 伤残金额核算 ─────┤
                                                                        ↓
                                                            [受领人与给付条件]
```

### 4.2 阶段如何落到这份 JSON

| 展开哪一块 | 局部图保留的真实结构 | 阅读重点 |
|---|---|---|
| 共同前提 | ENTRY_INSURANCE、IDENTITY、TERMS_REVIEW、C01、DEFINITION_REVIEW、C02、C03、X01，末端衔接 B01 | 默认再分“合同与保障”“意外与因果”“免责”三组。定义争议停在 DEFINITION_REVIEW 时，即使案例含有免责关键词，也只显示已走到的判断 |
| 身故 | D01 分普通／宣告两行。普通经 D02 到 D04；宣告经 D03、D05，未生还走 DECLARED_PASS、D07；已生还进入 D06 及 REFUND 系列 | 两条身故行各有保额时点；返还分支有独立终点。读者能看出普通身故的 180 日判断只在上行 |
| 伤残 | A01 分为 A02／A04，两路在 A05 汇合；A_MULTI 及其复核支路再汇入 A_ASSESSMENT_PASS；A06 分 A07／A08，最终汇入 A09 | 固定三个汇合点的位置。用户能同时看到治疗未结束如何切换评定时点，以及两种比例算法如何共用限额 |
| 共用给付条件 | BENEFICIARY → RECIPIENT → PREMIUM_SETTLEMENT 及对应结果 | 顶部显示从 D04、D07 或 A09 中哪一处进入。结果按“责任效果／金额／受领人／给付条件”分别列出，便于理解金额已确定、给付仍待履行的情形 |

**共享出口就近呈现。** 判断卡右侧优先画继续执行的分支；导致流程停止的出口贴在卡片下方，以“需补材料”“需复核”“本项不成立”等短标签表示。标签指向同一个真实结果 ID，点击可展开完整终点及“由哪些判断进入”。多个出口指向同一终点时，按出口分别保留文字和出边 ID。运行案例命中折叠出口时，就地展开这一条边与停止原因，无需让用户追一条穿越全图的线。

### 4.3 不同信息采用不同的阅读形式

| 对象 | 收起时 | 点开后 |
|---|---|---|
| 判断／分流 | 一个中文问题，边上写业务答案，如“普通身故／宣告死亡”“命中免责／未命中” | 展示事实值、核验状态、条件如何组合，以及所有可选出口。缺资料、事实冲突、已核实为否分别标注 |
| X01 免责 | 主图只占一个判断位置，节点注明“16 项免责” | 右侧用条款顺序的清单，支持“全部／本例已检查”。每项可展开条件和例外，例如 EX07 分成“未遵医嘱用药导致伤亡”和“按说明使用非处方药的例外”两行。显示未访问、未知、成立、不成立或需复核；例外只作用于所属子条件 |
| 计算节点 | 节点显示核算对象，案例运行后增加金额和单位或“待核定” | 明细按“输入及来源 → 中间计算 → 限额校验 → 本步结果”排列。D04 示例逐行列出身故日保额 100 万元、身故前已付伤残金 20 万元、扣减后 80 万元、剩余限额 80 万元、本步 80 万元 |
| 跨责任关系 | 身故、伤残两行的阶段卡都提供“查看计算依赖”入口 | 仅展开当前节点读取的一跳依赖。D04 → RESP_DISABILITY 虚线标“读取历史已付”；AMOUNT01 标“读取时点保额”；LIMIT01 标“读取共享限额”。依赖细节可继续查看快照、金额及完整性。全图开启“责任关系”时，两项责任并列连接到同一个限额对象 |
| 原文与待核事项 | 卡片最多显示一个主条款号及其他依据数量 | 原文抽屉按引用展示准确段落及上下文；待核事项列出受影响的判断、仍需核实的资料。原文关联、逻辑包含、历史数据读取各有独立位置 |

### 4.4 案例模式如何使用同一张图

选择案例后保持总览各阶段位置，用序号和粗实线标出已走流程。长路径中已通过的共同前提收成一段“已走 N 步”，点击可逐步核查。当前步骤展开为“上一步 → 当前节点 → 实际下一步”，相邻的备选出口以细线保留，并写明“未走”。依赖连线单独标记“已读取／缺失／冲突”。键盘切换上一步、下一步时只移动焦点，避免每一步都重排整张图。

**两例对照需要两种差异标记。** 对比第 180 日与第 181 日普通身故，在 D02 标“出口改变”，让用户看见一个案例进入 D04，另一个到 OUT_DEATH_FAIL。对比“无历史给付”与“已付 20 万元”，两例可以经过完全相同的节点和出口；此时在 D04 标“金额改变”，并排显示扣减项和结果。若把后者的账本改为完整性未知，D04 同时标“依赖缺失”和“出口改变”，保留此前已通过的责任效果。比较时共用一个布局，以步骤及字段标出首个差异，可切换查看后续差异。

### 4.5 布局实现和专项验收

分组配置按节点 ID 维护，每个流程节点归入一个主阶段。前端根据原边生成折叠组的入口、出口，保存每个视觉出口对应的真实边集合；案例高亮按实际出边 ID 匹配，杜绝只因两个节点相邻就点亮错误出口。默认关闭自由拖动，使用稳定的层级顺序及身故、伤残两行的固定顺序。屏宽不足时先将详情改为抽屉，再将局部流程切为纵向步骤；全文、完整图和全部异常出口均可主动打开。

专项验收时请审核者实际完成三件事：① 从责任总览进入宣告死亡分支，指出“未生还”和“已生还”的不同终点；② 从伤残两种评定时点找到共同的 A05，确认共享判断只显示一份；③ 在一个路径相同、金额不同的案例对中，从差异标记找到 D04 的输入变化及 2.1.1 对应原句。再由开发侧验证折叠、搜索定位、切换案例后，同一节点、出边、原文定位和选中状态始终一致。

### 4.6 页面操作与原文联动

**首次打开。** 顶部显示险种、条款版本，以及“浏览语义树／验证案例”。左侧为可搜索的条款目录，中间默认显示“保障前提 → 意外及免责 → 身故／伤残 → 金额核算 → 受领与给付条件”，右侧展示当前节点详情。用户展开一个阶段后再看到内部节点；阶段名称是展示分组，点击可查看包含的真实节点 ID。全图、返回上一级、适应视口和恢复上次位置均有明确入口。

**从原文查图。** 点击 2.1.1 第三段“身故前已给付伤残保险金”，高亮该段，右侧列出引用它的计算节点。选择 D04 即定位“意外身故保险金”；再打开“计算依据”，可以查看相关日期保额、已付伤残金和剩余限额。反向点击节点的“查看条款”可展开同段上下文，并保留返回图的位置。无映射段落显示“本版尚未建立节点关联”。

**从案例查原因。** 左侧切换为案例卡片，显示案例事实、待验证问题、条款预期。选中后运行案例，画布自动展开实际路径。右侧显示“条款预期／树的输出／差异”，下方列出责任效果、核算金额、缺少的资料和终点。点击任一步可查看所读事实、取值、命中规则、选中的出口、原文和下一步。点击“仅看本例”收起未走分支；退出后恢复先前视图。

**视觉约定。** 实线箭头表示流程；虚线与“读取”标签表示计算依赖，默认为收起；原文引用以可点击条款号呈现。经过的节点用粗边框和步骤序号，停止位置用图标和文字。边上写业务含义，例如 X01 的 true 标为“命中免责”，false 标为“未命中”。X01 展开后按条款顺序列出 16 项免责及其局部例外。汇入同一终点的多条边保留各自身份。提供键盘可操作的步骤列表，窄屏按“步骤／原文／图”切换。

## 五、数据与执行设计

1. **导入和校验。** 构建时读取两份源文件，记录版本与内容摘要。分别为节点、事实、规则、责任、依赖目标、来源建索引。检查重复 ID、未知操作符、悬空引用、入口可达性、流程或求值循环、原文行号与摘录。原文先按行建立定位，再渲染 Markdown，保留段落和列表位置；定位失配时显示具体来源 ID，进入重新核对清单。
2. **流程适配。** 按节点类型读取 `next`、`routes`、`cases`、`on_unknown`、`on_review`。边 ID 由起点、出口和终点生成。独立处理 `depends_on`、`responsibility_relations` 和 `source_refs`。例如 D04 读取 RESP_DISABILITY 的历史快照时，只亮起读取连线，伤残判断节点保持未访问。共享终点可折叠为出口标签，展开后仍定位同一真实节点。
3. **案例输入。** 每例保存编号、类型、叙述、已确认事实及其证据、保额时点、同合同同被保险人的给付快照、条款预期及审核状态。模板通过明确列出的已确认事实复用共用前提，缺项保持 unknown。自然语言叙述供阅读，首版以结构化字段驱动运算。
4. **独立求值。** 实现纯函数 `evaluate(graph, caseInput)`。从入口逐节点解释 JSON，仅支持执行契约列明的叶子和运算符。逻辑运算遵循 all／any／not 的未知值规则，保存实际读取顺序；已访问的争议或无效值走 review。分流按枚举选出口。计算节点先解析依赖、检查 guard，再按公式用十进制定点数计算。历史记录按作用域、日期、支付状态及唯一记录号核对，完整空账本可以取零；缺失账本走待补，冲突走复核。日期、外部鉴定和保额口径由带状态的输入提供。
5. **留存轨迹与效果。** 每一步记录节点 ID、出边 ID、输入值和状态、被访问规则、依赖绑定及来源 ID。输出保留 `code / effects / trace / missing_facts / missing_dependencies / amount`。责任通过后即使金额缺失仍保留责任效果；未知金额显示“待核定”，明确的零金额显示“0 元”。切换案例或改单个事实时从入口重新求值，清除上个案例的高亮与效果。
6. **独立对照。** 由条款审核者先读 Markdown 登记预期责任、金额、待核事项和依据段落，再由开发侧补录预期关键分支。运行器只接收图与案例输入。对照器分别比较终点、金额、关键分支与保留效果，标出首个可定位差异；预期尚有争议的案例单列“待确认”。修改示例事实后标为“自定义试算”，仅当存在相应的已审核预期时计入一致率。

建议将代码按 `data`（加载与校验）、`engine`（表达式、依赖、轨迹）、`cases`（输入及独立预期）、`views`（图、原文、结果对照）组织。后续接入已有工作台时，只需约定案例输入和执行结果接口，界面可消费同一轨迹格式。

## 六、首批可交给业务审核的案例

下表是设计预期，待实现后逐例运行。除特别注明，基准事实设为身份和保单相符、保障有效、同一意外导致伤亡、无适用免责、受领人明确、给付条件满足；固定保额和共享上限均为 100 万元，完整账本无先前给付。比例、事故认定和期间判断均作为已核实的合成输入。路径列只列辨别该案例所需的关键节点，网页展示完整轨迹。

| 类型与场景 | 条款预期 | 关键节点与核对点 |
|---|---|---|
| 常规 A：普通借款人遭遇交通意外，第 20 日因同一事故身故 | 2.1、2.1.1、2.3；局部通过，100 万元 | B01 → D01 → D02 → D04，最终 OUT_LOCAL_PASS；显示身故责任及责任终止效果 |
| 常规 B：治疗结束，180 日内形成标准所列单处伤残；无既有残疾，核实比例 10% | 2.1.2、2.3；局部通过，10 万元 | A01 → A02 → A05 → A_MULTI → A_ASSESSMENT_PASS → A06 → A08 → A09 |

## 八、实施顺序与交付物

按 1 名前端开发、1 名条款审核者阶段性参与估算，约 8–12 个开发工作日；专业口径确认时间另计。

| 阶段 | 估时 | 可评审交付物 |
|---|---:|---|
| 数据准备与案例定稿 | 1–2 日 | 数据校验清单、版本标识、基准事实模板、独立预期表；确定日期与历史账本的输入边界 |
| 图与原文浏览 | 2–3 日 | 可运行的浏览页面，用 D04 演示流程边、读取依赖和原文双向定位 |
| 案例求值与结果对照 | 3–4 日 | 可重复运行的规则解释器、案例集、单步轨迹、差异定位；身故和伤残各跑通一条完整路径 |
| 验收与交付 | 2–3 日 | 回归结果与未覆盖清单、可本地运行的静态包、启动说明；由审核者完成一次“从差异回到原文”的验收 |

首版采用独立网页以缩短验证周期，预留嵌入现有演示工作台的入口。首次评审优先确认两个问题：审核者是否能从结果快速回到决定性原句，以及当期望与计算不同，页面是否能指出究竟是哪一个事实、分支或金额输入导致差异。
